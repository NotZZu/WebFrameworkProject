# 응답속도·동시 처리 개선 측정 보고

측정 조건: 로컬, gunicorn 1 워커·8 스레드, SQLite 파일 DB(사용자 431명·신청 3,010건·검증서 약 1,500건), 클라이언트 동시 16, 시나리오당 400건. 도구는 `webservice/tools/load_seed.py`(데이터 생성)와 `webservice/tools/loadtest.py`(측정)이다. 같은 DB 복사본에 개선 전(origin/main)과 개선 후 코드를 각각 돌렸다.

| 시나리오 | 개선 전 중앙값 | 개선 후 중앙값 | 개선 전 초당 | 개선 후 초당 |
|---|---|---|---|---|
| 대시보드(기관) | 943 ms | 63 ms | 15.9 | 242.5 |
| 관리자 요약 | 1,072 ms | 65 ms | 14.4 | 234.9 |
| 신청 목록 1쪽 | 61 ms | 46 ms | 252.6 | 334.6 |
| 검증서 목록 | 335 ms | 55 ms | 43.4 | 278.3 |
| 개인 대시보드 | 52 ms | 43 ms | 297.3 | 355.2 |
| 신청 생성(쓰기) | 42 ms | 37 ms | 312.1 | 393.0 |
| 로그인(bcrypt) | 1,202 ms | 1,127 ms | 6.4 | 7.0 |

오류는 두 측정 모두 0건이다.

## 원인과 조치

- 기관 대시보드·관리자 요약·검증서 목록: 전체 신청·검증서를 읽어 파이썬에서 세고 정렬했다. 데이터가 늘수록 선형으로 느려진다. DB 의 GROUP BY·LIMIT·COUNT 로 바꿨다.
- 검증서 목록: 쪽마다 검증서 수만큼 신청을 한 건씩 조회했다(N+1). 한 번에 조회한다.
- SQLite: 쓰기가 읽기를 막고, 잠기면 바로 오류가 났다. WAL 과 busy_timeout 10초를 켜고 조회용 색인 4개를 만들었다.

## 한계

- 개인 대시보드는 처음 개선했을 때 52 → 81 ms 로 느려졌다. 단일 요청 CPU 를 재 보니 0.63 → 1.90 ms 였다(질의 4개 → 7개). 본인 범위는 데이터가 적어 한 번에 읽어 계산하는 방식으로 되돌려 43 ms 가 되었다(옛 코드 0.82 ms, 새 코드 0.73 ms/요청). 본인 신청이 수천 건이 되면 이 경로는 선형으로 느려진다.
- 로그인은 bcrypt 비용 때문에 1초대이며 의도된 보안 비용이라 바꾸지 않았다.
- DynamoDB 는 SQL 처럼 DB 가 세어 주지 못해, 목록을 읽어 계산하는 방식이 남는다. AWS 실측은 아직 하지 않았다.
- 1 워커·로컬 측정이므로 절대값이 아니라 개선 전후 비교로 읽어야 한다.

## DynamoDB 읽기량 (프로비저닝 10 RCU 보호)

SQL 용 개선을 넣은 직후 DynamoDB 는 같은 목록을 메서드마다 다시 읽어 읽기량이 오히려 늘었다. 모의 환경(moto)에서 신청 210건·검증서 105건으로 실제 항목 크기를 재어 강한 일관성 읽기(4KB 단위) 기준으로 환산했다.

| 화면 | 개선 전 | SQL 개선 직후 | 수정 후 |
|---|---|---|---|
| 기관 대시보드 | 약 25 RCU | 약 53 RCU | 약 25 RCU |
| 관리자 요약 | 약 25 RCU | 약 39 RCU | 약 25 RCU |
| 개인 대시보드 | 약 4 RCU | 약 6 RCU | 약 4 RCU |

조치: 한 요청(저장소 객체) 안에서는 같은 목록을 한 번만 읽고 쓰기가 있으면 비운다. 최근 N건은 sk 가 시각순이라 역순 Query 에 Limit 을 걸어 N건만 읽는다.

한계: 신청이 늘면 읽기량도 선형으로 늘어난다(전체 목록을 읽는 방식 그대로). 210건에서 기관 대시보드는 25 RCU 라 10 RCU/초 한도에서 초당 0.4회 정도만 처리한다. 근본 해결은 상태별 건수를 미리 세어 두는 카운터 항목이며, 이번 범위에는 넣지 않았다.

## AWS 소량 측정 (Lambda + DynamoDB 프로비저닝 10/10)

조건: CloudFront → Lambda(512MB) → DynamoDB, 기관 1명·개인 30명·신청 210건·검증서 105건, 동시 2, 브라우저(같은 출처)에서 호출. 시나리오당 20~40건. 개선 전은 11월 9일 배포 코드, 개선 후는 feature/perf-load(8c59c9d) 배포 코드(코드 해시로 확인). 오류는 양쪽 모두 0건이다.

| 시나리오 | 개선 전 중앙값 | 개선 후 중앙값 | 개선 전 95% | 개선 후 95% |
|---|---|---|---|---|
| 대시보드(기관) | 343 ms | 341 ms | 3,553 ms | 3,518 ms |
| 관리자 요약 | 399 ms | 356 ms | 7,034 ms | 3,609 ms |
| 신청 목록 1쪽 | 200 ms | 200 ms | 3,380 ms | 3,380 ms |
| 검증서 목록 | 322 ms | 373 ms | 3,500 ms | 1,924 ms |
| 개인 대시보드 | 121 ms | 121 ms | 895 ms | 485 ms |
| 신청 생성 | 67 ms | 65 ms | 73 ms | 838 ms |
| 로그인 | 1,060 ms | 1,099 ms | 1,078 ms | 1,117 ms |

DynamoDB 읽기 용량(CloudWatch, 측정 구간 합): 개선 전 약 2,527 RCU·읽기 제한 73건, 개선 후 약 2,505 RCU·읽기 제한 83건. Lambda 오류 0건, 콜드 스타트 초기화는 약 0.3초.

해석: 로컬(SQLite)에서 본 10배 이상의 개선은 AWS 에서 나타나지 않았다. DynamoDB 는 DB 가 세어 주지 못해 전체 목록을 읽는 방식이 그대로이고, 이번 수정은 그 읽기량을 개선 전 수준으로 유지한 것이기 때문이다. 95% 값이 3~7초로 튀는 것은 읽기 제한(10 RCU/초 초과) 뒤 SDK 재시도 대기이며, 콜드 스타트가 아니다. 중앙값이 비슷한 것은 제한이 걸리지 않은 요청이 대부분이기 때문이다.

한계: 데이터 210건, 동시 2의 스모크 수준이다. 로컬 3,010건·동시 16 측정과 직접 비교하지 않는다. 읽기 한도를 늘리면 무료 한도(25)를 넘을 수 있어 하지 않았다.

다음 개선 후보(DynamoDB): 상태·알고리즘별 건수와 최근 N건을 쓰기 때 갱신하는 집계 항목(카운터)으로 두면 대시보드 읽기가 신청 수와 무관하게 1~3 RCU 가 된다.

### DynamoDB 읽기량 2차 개선

| 화면 | 개선 전 | 1차 수정 후 | 2차 수정 후 |
|---|---|---|---|
| 기관 대시보드 | 약 25 RCU, 호출 4회 | 약 25 RCU | 약 13.5 RCU |
| 관리자 요약 | 약 25 RCU, 호출 4회 | 약 25 RCU | 약 13 RCU |
| 검증서 목록(10건, 기관) | 약 32 RCU, 호출 24회 | 약 32 RCU | 약 20.5 RCU, 호출 4회 |
| 개인 대시보드 | 약 4 RCU | 약 4 RCU | 약 4 RCU |

조치: 기관 전체 집계(대시보드·관리자 요약)는 최종 일관성 읽기(비용 절반)로 읽는다. 본인 범위와 목록 화면은 강한 일관성을 유지한다. 신청·사용자를 id 로 여러 건 가져올 때 한 건씩 읽던 것을 100개 단위 일괄 조회로 바꾸고(알고리즘·소유자는 바뀌지 않는 값이라 최종 일관성), 못 찾은 키만 강한 일관성으로 한 번 더 확인한다. 호출 횟수도 24회에서 4회로 줄어 지연이 준다.

트레이드오프: 기관 대시보드 숫자가 방금 한 변경을 아주 잠깐(보통 1초 안) 늦게 반영할 수 있다.

한계: 신청 수에 비례해 읽는 구조는 그대로다. 읽기를 신청 수와 무관하게 만들려면 집계 항목(카운터)과 갱신순 색인이 필요하며 데이터 모델·기존 데이터 이전이 따르는 별도 작업이다.

### 느린 요청 원인 확인 (검증서 목록 100건, 동시 2)

20건 측정에서 95% 값이 3.4초로 나온 이유를 확인하려고 100건으로 늘리고 요청별 시간을 남겼다.

- 결과: 중앙값 174 ms, 95% 3,369 ms, 최대 6,906 ms. 100건 중 12건이 1초를 넘었고 모두 2건씩 쌍으로 나타났다. 시간은 약 3.36초(8건)와 약 6.5~6.9초(4건) 두 가지뿐이다.
- 위치: Lambda 실행 기록에서 느린 호출의 Duration 이 3.25초, 6.45초, 6.8초였고 정상 호출의 중앙값은 71 ms 였다. 느린 시간은 네트워크나 CloudFront 가 아니라 Lambda 안에서 쓰였다. 같은 분에 DynamoDB 읽기 제한 31건이 기록됐다.
- 크기가 일정한 이유: AWS SDK 의 DynamoDB 재시도 대기는 0.05초에서 시작해 두 배씩 늘어난다(0.05+0.1+0.2+0.4+0.8+1.6 = 3.15초). 3.25초는 이 대기에 호출 시간을 더한 값이고, 6.5초는 두 번 겹친 값이다. SDK 로그로 직접 확인하지는 않았고 값의 일치에 근거한 해석이다.
- 같은 주소 동시 호출 때문이 아님: 주소마다 다른 인자를 붙여 60건을 다시 측정해도 같은 쌍(6.49초 2건)이 나타났다. 이때 중앙값은 91 ms, 95% 292 ms 였다.
- 미해결: 브라우저에서 본 느린 요청은 12건인데 Lambda 의 느린 호출 기록은 6건이었다. 원인을 맞추지 못했다.

결론: 소수의 요청이 읽기 제한 때문에 약 3초를 대기하는 것이 95% 값을 결정한다. 요청 수가 적을수록 이 몇 건에 95% 값이 좌우되므로, 소량 측정에서는 중앙값을 기준으로 읽는다.
