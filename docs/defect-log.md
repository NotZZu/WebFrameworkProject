# 결함 기록 (공격 시험에서 발견)

공격 시험은 `webservice/tests/integration/test_attack_*.py` 에 있다. 시험은 "안전하게 동작해야 하는 쪽"을 단언하므로, 실패하면 결함이다.
발견된 결함의 시험은 `tests/red_cases.txt` 에 올려 두었다가(Red), 수정이 끝나면 지운다(Green).

## 1단계: SC-01 인증 / SC-02 대시보드 (시험 20종, 실행 37건)

결과: 통과 26건 / 결함 11건 발견. 2단계에서 11건 모두 수정해 37건 전부 통과.

| 결함 | 시험 | 공격 | 기대 | 실제 | 심각도 | 상태 |
|---|---|---|---|---|---|---|
| DF-01 | IT-ATK-02 | 한글 비밀번호(30자+영문숫자, 90바이트 초과)로 가입한 뒤, 72바이트 뒤쪽만 다른 비밀번호로 로그인 | 401 | 200 (로그인 성공) | 높음 | 수정 완료 |
| DF-02 | IT-ATK-12 | 같은 계정에 비밀번호를 12번 연속 틀림 | 429 등으로 제한 | 계속 401만 반환, 제한 없음 | 높음 | 수정 완료 |
| DF-03 | IT-ATK-13 | 로그아웃 전 세션 쿠키를 저장해 두었다가 로그아웃 뒤 재사용 | 401 | 200 (세션이 서버에서 무효화되지 않음) | 높음 | 수정 완료 |
| DF-04 | IT-ATK-14 | 환경변수 `SECRET_KEY`가 없을 때 기본 키(`dev-secret-change-me`)로 세션 쿠키를 만들어 제출 | 기동 거부 또는 401 | 200 (기관 사용자로 위조 로그인 성공) | 높음 | 수정 완료 |
| DF-05 | IT-ATK-09 | 10만 단계로 중첩된 JSON 본문 전송 | 400 | 500 (RecursionError) | 중간 | 수정 완료 |
| DF-06 | IT-ATK-11 | 2MB 크기 본문 전송 | 413 | 401 (끝까지 읽어서 처리, 크기 제한 없음) | 중간 | 수정 완료 |
| DF-07 | IT-ATK-06 | 기관 코드에 1만 자, 제어문자 입력 | 400 (설계서 VARCHAR(50)) | 201 (그대로 저장) | 중간 | 수정 완료 |
| DF-08 | IT-ATK-15 | 응답 보안 헤더 확인 | nosniff, 프레임 삽입 차단 | 헤더 없음 | 중간 | 수정 완료 |
| DF-09 | IT-ATK-16 | 세션 쿠키 Secure 속성 확인 | 켜짐 | 꺼짐 (HTTP로도 쿠키 전송) | 중간 | 수정 완료 |
| DF-10 | IT-ATK-03 | 비밀번호에 NUL(\x00) 포함 | 400 | 201 (제어문자 허용) | 낮음 | 수정 완료 |
| DF-11 | IT-ATK-04 | 아라비아-인도 숫자만으로 "숫자 1자 이상" 규칙 통과 시도 | 400 | 201 (정규식 `\d` 가 유니코드 숫자 허용) | 낮음 | 수정 완료 |

### 공격했지만 견딘 것 (통과 26건)
- 최대 길이(64자) 비밀번호의 마지막 글자 구분 (IT-ATK-01)
- 아이디 변형 7종: 줄바꿈, 앞뒤 공백, 전각 문자, 제로폭 문자, 길이 초과/미달 (IT-ATK-05)
- SQL 인젝션 문자열 3종, users 테이블 변화 없음 (IT-ATK-07)
- 필드 타입 혼동 12종: 배열, 객체, 숫자, null (IT-ATK-08)
- JSON 아닌 요청: form, 빈 본문, 배열, 문자열 (IT-ATK-10)
- 로그인 실패 응답이 계정 존재 여부를 드러내지 않음 (IT-ATK-17)
- 대시보드에 `user_id`, `scope` 쿼리를 붙여도 무시됨 (IT-ATK-18)
- 삭제된 사용자의 세션으로 대시보드 접근 시 401 (IT-ATK-19)
- 같은 아이디로 12개 요청 동시 가입: 201 한 번, 나머지 409, 서버 오류 없음 (IT-ATK-20)

### 참고 (수정 시 고려할 점)
- DF-09는 단순히 Secure를 켜면 `http://13.209.215.10` 직접 접속에서 로그인이 안 된다. CloudFront(HTTPS) 주소만 쓰는 조건에서 켜야 하므로 환경변수로 제어한다.
- DF-04는 운영 서버에는 `SECRET_KEY`가 주입되어 있지만, 빠졌을 때 조용히 기본 키로 동작하는 것이 문제다.
- DF-03은 쿠키에 세션을 담는 구조라 서버에서 무효화할 수 없다. 사용자별 세션 버전을 DB에 두는 방식으로 고쳐야 한다.

### 2단계 수정 상세 (원인, 위치, 재검증)

| 결함 | 원인 | 수정 위치 | 재검증 | 부작용·한계 |

| DF-02 | 로그인 실패 횟수를 세는 곳이 없었다 | 새 파일 `app/throttle.py`, `api/auth.login` | IT-ATK-12, UT-ATK-01~03 통과 | 서버 재시작 시 초기화, 남의 아이디를 일부러 잠글 수 있음 |
| DF-03 | 세션을 쿠키에만 담아서 서버가 무효화할 수 없었다 | `models.ActiveSession`(새 테이블), `auth_service.start_session/end_session/user_for_session`, `helpers.session_user` | IT-ATK-13 통과 | 배포 시 기존 로그인 1회 풀림 |

수정 전 상태는 공격 시험이 실패하는 것으로 확인했고(1단계 커밋), 수정 후 같은 시험이 통과하는 것으로 확인했다(2단계 커밋). 시험 코드는 수정하지 않았고, 두 곳(IT-ATK-09 본문 크기, IT-ATK-16 환경변수 준비)만 수정 후 조건에 맞춰 보강했다.

## 3단계: SC-04 CAVP 시험 신청

공격 시험은 아직 추가하지 않았다(5단계 동시성 시험과 6단계 화면별 공격에서 다룬다).
구현 방식 메모: 중복 신청 방지는 "개수를 세고 저장하는" 단순 방식으로 구현했다. 동시에 같은 신청이 들어오면 둘 다 통과할 수 있어서 5단계에서 시험한다.

## 4단계: SC-05 CAVP 진행상태 조회·심사

공격 시험은 아직 추가하지 않았다. 5단계(동시성)와 6단계(화면별 공격)에서 다룬다. 구현 중 시험으로 잡은 결함만 기록한다.

| 결함 | 발견 시험 | 내용 | 원인 | 수정 | 심각도 |
|---|---|---|---|---|---|
| DF-12 | ST-05-N3, ST-05-N4 (브라우저 E2E) | 기관 사용자가 아닌 상태나 맞지 않는 단계에서도 "승인", "반려" 버튼이 화면에 보임 | 버튼 CSS `display:inline-block`이 HTML `hidden` 속성을 덮어씀 | `[hidden]{display:none !important}` 추가 | 낮음 (서버가 막아 주지만 화면이 잘못된 동작을 유도) |

구현 방식 메모
- 서비스의 상태 변경은 "읽고, 검사하고, 쓰는" 단순 방식이다. 기관 둘이 같은 신청을 동시에 처리하면 나중 요청이 앞 요청의 결과를 덮어쓸 수 있어서 5단계에서 시험한다.
- 기관 사용자의 신청 목록은 전체 범위(`scope=all`)로 돌려준다. 심사하려면 타인 신청이 보여야 하고, 대시보드의 기관 범위와 같은 규칙이다. 일반 사용자는 본인 신청만 본다.
- 설계서 SC-08(관리자 대시보드, 선택)의 "상태 변경" 기능이 이 화면에 먼저 들어갔다.

## 5단계: 동시성 공격 시험 (시험 4종)

여러 요청을 `Barrier`로 같은 순간에 출발시켜 실제 서버처럼 겹치게 보냈다(파일 DB 사용). 결과: 통과 1건 / 결함 3건 발견.

| 결함 | 시험 | 공격 | 기대 | 실제 | 심각도 | 상태 |
|---|---|---|---|---|---|---|
| DF-13 | IT-ATK-21 | 같은 사용자가 같은 알고리즘을 16개 요청으로 동시에 신청 | 201 한 건, 나머지 409 | 중복 신청이 2건 저장됨 (매번 재현) | 높음 | 수정 완료 |
| DF-14 | IT-ATK-22 | 기관 사용자가 같은 심사중 신청을 승인 6건, 반려 6건으로 동시에 처리 | 성공 한 건 | 승인과 반려가 여러 건 성공하고 최종 상태가 어느 요청의 결과인지 불일치 (5라운드 중 일부에서 재현) | 높음 | 수정 완료 |
| DF-15 | IT-ATK-24 | 같은 계정에 틀린 비밀번호 24건을 동시에 전송 | 5건 이하만 검사하고 나머지는 429 | 24건 모두 비밀번호 검사까지 진행 (시도 제한 우회) | 높음 | 수정 완료 |

견딘 것: 서로 다른 알고리즘 7종 동시 신청은 모두 201로 처리되고 DB 잠김 오류도 없었다(IT-ATK-23).

원인 분석
- DF-13: "이미 있는지 세고, 없으면 저장"이 두 단계로 나뉘어 있어서 그 사이에 다른 요청이 끼어들 수 있었다. 3단계에서 단순하게 구현한 부분이 그대로 드러났다.
- DF-14: "상태를 읽고, 허용 전이인지 검사하고, 쓰는" 세 단계 사이에 다른 요청이 끼어들 수 있었다. 4단계 메모에서 예상한 부분이다.
- DF-15: 2단계에서 만든 로그인 제한이 "검사 → 비밀번호 확인 → 실패 기록" 순서라서, 동시 요청은 기록되기 전에 모두 검사를 통과했다. 결함을 고친 코드가 다시 뚫린 사례다.

### 5단계 수정 상세

| 결함 | 수정 | 재검증 | 부작용·한계 |
|---|---|---|---|
| DF-13 | DB에 부분 유일 인덱스를 추가: 진행 중(접수/심사중)인 `(user_id, algorithm_type)`은 한 건만 저장 가능(`db.init_db`). 서비스는 인덱스 위반을 409 `DUPLICATE_APPLICATION`으로 변환(`cavp_service.create_application`) | IT-ATK-21 통과 (8회 반복 실행 모두 통과) | 기존 시험 데이터 2곳이 이 규칙을 어기고 있어서(같은 알고리즘의 진행 중 신청 여러 건) 서로 다른 알고리즘으로 고쳤다. 운영 DB에 이미 중복이 있으면 인덱스 생성을 건너뛴다 |
| DF-14 | 상태 변경을 "내가 읽은 상태일 때만 바꾸는" 한 번의 UPDATE로 처리(`cavp_service.update_status`). 영향 행이 0이면 409 `INVALID_TRANSITION` | IT-ATK-22 통과 (5라운드 × 8회 실행 모두 통과) | 늦게 도착한 요청은 "다른 요청이 먼저 변경했습니다"라는 안내를 받는다 |
| DF-15 | 로그인 제한을 "검사 후 기록"에서 "자리를 먼저 차지(`try_acquire`)한 뒤 비밀번호 확인"으로 변경 (`throttle.py`, `api/auth.login`) | IT-ATK-24, UT-ATK-04 통과 | 실패만이 아니라 시도 전체를 먼저 세고 성공하면 초기화한다 |

DF-15는 2단계에서 고친 결함이 동시 요청에는 여전히 뚫려 있던 경우다. 수정의 효과를 같은 방식의 공격으로 다시 확인해야 한다는 점을 보여 준다.
